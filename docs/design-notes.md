# Design notes

Why the exporters work the way they do. These lessons came from running them against busy production
SMS gateways – read this before changing counter logic or dashboard queries.

## One central exporter, many gateways

Each exporter scrapes the HTTP status page of **many** gateway servers in parallel (`max_workers`) and exposes a
single `/metrics` endpoint. Every series carries a `server` label (the target `name` from the config).
Benefits: one place to configure passwords, no software on the gateways, one Prometheus job per gateway type.
Scraping happens on the exporter's own timer (`scrape_interval`), not on Prometheus' request, so a slow gateway
never makes a Prometheus scrape time out.

## smppbox: session counters reset – the `SessionAccumulator`

smppbox only reports counters **per SMPP session**, and they start at zero every time a customer re-binds.
A naive `sum()` would go backwards on every reconnect. The exporter therefore builds monotonic per-customer
counters by adding per-session deltas. Three traps were found in production:

1. **Restart = burst.** After an exporter restart, adding the full history of long-running sessions looked like
   billions of messages in one scrape (a 24 000 msg/s spike). Fix: the first scrape after start only records a baseline.
2. **Session gaps.** A session that disappears from a single scrape (partial page, network glitch) was treated as
   new when it came back and its whole history was added again – about 23× in 12 h. Fix: vanished sessions are
   remembered for 1 h and continue from their last value; only sessions younger than `2 × interval + 30 s` count
   from zero; older unknown sessions are a baseline.
3. **Safety net.** Any per-scrape increase above `max_customer_rate × window` is discarded as a glitch.

If bad data already reached Prometheus, delete it with the admin API (see [troubleshooting](troubleshooting.md)).

## KSMPPD: the TPS model

KSMPPD's load triplet is *since start / last 1 s / last 60 s*; bind type `1/2/3` = transmitter / receiver /
transceiver. Customer counters survive bind drops, so no accumulator is needed.

* **TPS limit** = `max-inbound-load` of the customer – one limit for the whole customer, regardless of the
  number of binds (an earlier per-bind model was wrong).
* **Achieved TPS** = inbound (MT accepted + rejected) + outbound (DLR + MO).
* **Utilisation** = achieved / limit, **headroom** = limit − achieved.
  Example: 13.11 in + 13.0 out = 26.11 TPS → 26.11 % of a 100 TPS limit.

## Kannel bearerbox

* Load triplet = last 60 s / 300 s / since start. SMSC status words (`online`, `re-connecting`, `dead`, …) map to
  a numeric state.
* `instances = N` produces several SMSCs with the same admin-id – they get unique suffixes `#2`, `#3`.
* A wrong password returns **HTTP 200** with `<gateway>Denied</gateway>`. It is detected and reported as `up 0`.
* SMSC names such as `SMPP:198.51.100.7:2775/2775:ESME_DEMO_01:smpp` are parsed into protocol, host, port,
  receive port, SMSC username and system-type (`kannel_smsc_connection_info`).
* Kannel-HA adds HA routes, SMSC queue types and per-box counters – exported when present.

## Grafana: tables must have identical label sets

Grafana's *merge* transformation joins table queries into one row only when their label sets are identical.
Raw series carry `job`/`instance`, aggregated ones do not – the result was split rows. **Every table query is
wrapped in `max by (<key labels>)`**, and joins use `on (server, esme)`.

Customer tables only list customers of servers that are currently reporting, otherwise `increase(...[range])`
columns keep showing "ghost" rows of removed servers.

## Generated dashboards

The dashboard JSON is generated by `tools/gen_*_dashboard.py` – edit the generator, never the JSON. This keeps
75+ panels consistent (descriptions, units, colours, layout) and makes reviews readable.
